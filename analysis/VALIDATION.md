# Проверка стенда

Перед сравнением подходов нужно проверить сам способ измерения. Если при одинаковой конфигурации результаты постоянно меняются из-за условий запуска, разницу между подходами будет трудно объяснить. Для этого отдельно проверяются повторения одной конфигурации, нагрузка и порядок прогонов.

## Что проверяется

При проверке стенда необходимо оценить несколько составляющих.

1. Доступность сервисов и корректность обработки изображения.
2. Различия между группами одинаковых запусков в A/A-серии.
3. Нагрузку на CPU и наличие ограничений со стороны контейнера.
4. Изменение времени выполнения по порядку прогонов.

Команда make smoke проверяет сервисы, происхождение WASM-файла и результаты последовательной обработки для трёх подходов.

## Запуск A/A

A/A запускается командой EXPERIMENT_CPUS=6 make aa.

В configs/aa.json заданы десять повторений подхода shared со сценарием sequential.

Для каждого прогона создаётся новый браузер.

После запуска укажите выведенный каталог серии.

    make validate BATCH=results/raw/имя-серии

## Параметры и сравнение групп

Параметры проверки находятся в configs/validation.json.

Уровень значимости равен 0,05, сид разделения на группы равен 20261112, порог внимания к CPU равен 80%, число перестановок для проверки тренда равно 9999.

validate_stand.py разделяет десять прогонов на группы A1 и A2 по пять.

Разбиение выполняется один раз с фиксированным сидом и сохраняется в aa-groups.csv.

Для сравнения перебираются все 252 разбиения и сопоставляются суммы рангов. Результат учитывает одинаковые значения.

Для трёх временных метрик применяется поправка Холма.

Также сохраняются размер эффекта, медиана, IQR и интервал общей выборки из десяти прогонов.

A/A проверяет одну конфигурацию.

Отсутствие различия при пяти наблюдениях в каждой группе не доказывает эквивалентность и не распространяется автоматически на все сценарии.

Сид и состав групп нельзя подбирать после просмотра результата.

## Стабильность измерений

Для конфигураций с десятью и более прогонами проверяется ранговая связь времени с порядком запуска.

Вероятность оценивается по перестановкам с фиксированным сидом.

Поправка Холма применяется ко всем проверкам тренда серии.

Даже при отсутствии значимого монотонного тренда нужно посмотреть графики. Скачки или немонотонные изменения могут остаться незамеченными тестом.

## Нагрузка и ограничения ресурсов

CPU контроллера измеряется относительно одного ядра.

CPU контейнера включает браузер и нормируется на квоту из cpu.max.

Записываются показатели за сценарий и за более длинный интервал с запуском браузера.

Память фиксируется в конце интервала, а не в момент максимального потребления.

Отсутствие счётчиков даёт неполный результат проверки.

Превышение порога CPU или наличие троттлинга вызывает предупреждение.

Среднее значение за короткий интервал не показывает все пики.

Квота применяется по периодам планировщика, поэтому значение за короткий интервал может превышать 100%.

Высокую загрузку контейнера нельзя целиком приписывать управляющему процессу, поскольку в нём же работает браузер с исследуемым приложением.

## Файлы проверки

В results/processed/имя-серии/validation сохраняются aa.csv, aa-groups.csv и aa.png для A/A, trends.csv для проверки тренда, resources.csv и resources.png для нагрузки.

validation.json содержит машинный протокол, validation.txt его текстовое представление.

Успешное завершение команды означает, что отчёт создан, а не что все проверки пройдены.

## Результаты выполненных проверок

В предварительных запусках с квотой 2 CPU обнаружен троттлинг.

При 4 CPU он не повторился, но в пользовательской A/A-серии нагрузка контейнера доходила до 89,44% квоты.

В следующей серии с 6 CPU максимум составил 60,14%, троттлинга не было.

Основные серии выполнялись с квотой 6 CPU.

Снижение процента от увеличенной квоты не означает уменьшения вычислительной работы.

Для итогового сравнения использованы основные серии от 12 и 13 ноября 2026 года, указанные в results/README.md.

В обеих не обнаружено значимого монотонного тренда и троттлинга.

Максимальная средняя загрузка контейнера во время сценария составила 73,08% и 66,37% квоты соответственно.

Основные выводы о числе экземпляров, памяти и преимуществах общей среды в двух сценариях воспроизвелись.

Абсолютные времена и разброс между сериями различались.
