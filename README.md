# Эксперимент с общим WASM-компонентом

В данном проекте реализован экспериментальный стенд для сравнения способов подключения WASM-компонента к микрофронтендам. Исследование проводится на примере обработки изображения.

Приложение включает три отдельно собираемые части, которые выполняют фильтрацию, преобразование и анализ. Для вычислений используется один и тот же WASM-компонент. При этом способ его подключения можно менять.

Цель эксперимента заключается в том, чтобы определить, как организация доступа к компоненту влияет на время выполнения операций, число созданных экземпляров и потребление линейной памяти.

Для этого необходимо выполнить несколько действий.

1. Проверить работу приложения и корректность обработки изображения.
2. Оценить разброс измерений при повторении одной конфигурации.
3. Выполнить серию прогонов для трёх подходов к интеграции.
4. Сравнить полученные показатели и проверить нагрузку во время измерений.
5. Повторить основную серию и сопоставить результаты.

## Что сравнивается

| Подход | Доставка файла | Работа с экземпляром |
| --- | --- | --- |
| local | Каждый микрофронтенд получает свою копию WASM-файла | Каждый создаёт собственный экземпляр |
| server | Микрофронтенды загружают файл по общему адресу | Экземпляры остаются отдельными |
| shared | Файл загружается через общий JavaScript-модуль | Микрофронтенды обращаются к одному экземпляру |

Таким образом, в эксперименте меняется организация доступа к WASM. Вычислительные функции и исходное изображение остаются одинаковыми.

Файл WASM содержит программу. Экземпляр появляется после её подготовки к выполнению и имеет собственную линейную память. Общий адрес файла сам по себе не означает общую память.

Исходное изображение размером 640 × 420 пикселей создаётся программно. Для каждого подхода выполняются три сценария.

| Сценарий | Последовательность действий |
| --- | --- |
| sequential | Перевод в оттенки серого, уменьшение до 320 × 210 и анализ |
| concurrent | Одновременное первое обращение фильтрации и уменьшения к исходному изображению |
| repeated | Инверсия, горизонтальное отражение, анализ, изменение яркости и вертикальное отражение |

В concurrent результаты двух операций сохраняются отдельно. Данный сценарий позволяет проверить работу при одновременных обращениях, но не означает выполнение вычислений на нескольких ядрах.

Один прогон включает запуск нового процесса браузера и выполнение одного сценария с выбранным подходом.

Основная серия содержит 90 прогонов. Для каждого сочетания подхода и сценария предусмотрено десять повторений. Порядок запуска перемешивается с фиксированным сидом 20261112, поэтому при повторении серии сохраняется тот же план.

Параметры находятся в *configs/experiment.json*.

## 1. Подготовка компьютера

Для запуска потребуется установить несколько инструментов.

| Инструмент | Для чего используется |
| --- | --- |
| Git | Получение проекта и фиксация версии кода |
| Node.js 24 | Подготовка запуска и сбор сведений об окружении |
| make | Выполнение команд из Makefile |
| Docker с Compose | Запуск серверов, браузерных прогонов и анализа в контейнерах |

На macOS можно использовать Docker Desktop, на Linux Docker Engine с Compose. Для Windows команды выполняются в WSL с доступом к Docker. Инструкция рассчитана на bash или zsh.

Перед выполнением команд запустите Docker.

В сохранённых основных сериях экспериментальному контейнеру задавалась квота 6 CPU и 2 ГиБ памяти. Серверы работали отдельно. Для повторения этих условий Docker должен иметь доступ как минимум к шести CPU и достаточной памяти для всех контейнеров.

Квота ограничивает использование процессора, но не резервирует физические ядра. Если используется Docker Desktop, ресурсы его виртуальной машины настраиваются отдельно от ресурсов самого компьютера.

Проверьте инструменты.

    git --version
    node --version
    make --version
    docker compose version
    docker info

Node.js должен вывести версию v24.x. В выводе docker info должна присутствовать информация о сервере без ошибки подключения.

Для первой сборки нужен интернет, поскольку Docker скачивает образы и зависимости.

Python, Chromium и npm-зависимости устанавливаются внутри контейнеров. Отдельно устанавливать их на компьютер для данного способа запуска не требуется. Локальный Node.js используется сценарием подготовки эксперимента.

## 2. Получение проекта

    git clone https://github.com/sunecit/wasm-experiment.git
    cd wasm-experiment
    git status --short
    git rev-parse HEAD

Все дальнейшие команды выполняются из этой папки.

Пустой вывод git status --short означает чистую рабочую копию.

Последняя команда показывает версию кода. Данное значение будет записано в метаданные эксперимента.

## 3. Запуск приложения и проверка стенда

    make up
    docker compose ps

После успешного запуска откройте http://127.0.0.1:4175. В браузере можно выбрать подход и выполнить операции вручную.

Сервисы web и wasm-delivery должны работать и пройти проверку состояния.

Проверьте доставку WASM и работу трёх подходов.

    make smoke

Запустите функциональные браузерные тесты.

    make check

Команды собирают нужные образы автоматически. Дождитесь успешного завершения.

Если сервер не запускается, посмотрите сообщения.

    docker compose logs --tail=100 web wasm-delivery

Если порт 4175 занят, можно указать другой порт.

Используйте то же значение STAND_PORT и в последующих командах запуска.

    STAND_PORT=4176 make up

В этом случае страница доступна по адресу http://127.0.0.1:4176.

## 4. Проверка измерений на одинаковой конфигурации

A/A-серия повторяет подход shared со сценарием sequential десять раз. Она помогает проверить разброс измерений до сравнения разных подходов.

    EXPERIMENT_CPUS=6 make aa

После завершения команда выведет путь к созданной серии. Внутри контейнера он начинается с /workspace/results/raw/wasm-aa-.

На компьютере эта же папка находится в *results/raw* внутри проекта. Часть /workspace в локальном пути не используется.

Скопируйте имя созданной папки и сохраните путь в переменную.

В следующей команде замените ИМЯ_AA_СЕРИИ на полное имя из вывода.

    AA_BATCH="results/raw/ИМЯ_AA_СЕРИИ"
    make validate BATCH="$AA_BATCH"

Команда сначала рассчитывает таблицы и строит графики, затем проверяет A/A, нагрузку и изменение времени по порядку прогонов. Без BATCH она не знает, какую серию обрабатывать.

После обработки перейдите в *results/processed/ИМЯ_AA_СЕРИИ*.

1. Откройте *sequential-scenarioDurationMs.png* и посмотрите, как менялось время между прогонами.
2. В подпапке *validation* откройте *aa.png*, чтобы сопоставить две группы одинаковых запусков.
3. Посмотрите *resources.png* и прочитайте *validation.txt*. Проверьте, есть ли предупреждения о нагрузке и троттлинге.

Отсутствие статистически значимого различия не доказывает полного совпадения измерений. Поэтому вместе с результатом проверки рассматриваются сами графики и разброс значений.

## 5. Сохранение результатов проверок перед основной серией

Основная серия запускается только из чистой рабочей копии с Git-коммитом.

Проверки создают файлы в results и test-results, поэтому сначала сохраните их локально.

    git status --short
    git add results test-results
    git diff --cached --stat
    git commit -m "Результаты проверки стенда перед экспериментом"
    git status --short

Если Git сообщает, что сохранять нечего, дополнительный коммит не нужен.

Если остались изменения исходников или конфигурации, проверьте и сохраните их отдельно.

Последний git status --short должен ничего не вывести.

Отправлять коммит на GitHub для запуска не требуется.

Если Git ещё не знает автора, задайте свои имя и email для этого репозитория и повторите коммит.

    git config user.name "Ваше имя"
    git config user.email "ваш-email@example.com"

## 6. Основной эксперимент

Не меняйте конфигурацию и условия нагрузки между сравниваемыми сериями. На время измерений закройте тяжёлые приложения и не запускайте другие вычислительные задачи.

    EXPERIMENT_CPUS=6 make experiment

Дождитесь завершения всех 90 прогонов. В конце будет выведен новый каталог results/raw/wasm-integration-.... Он содержит исходные измерения, план, конфигурацию, сведения о компьютере и Docker, версии программ и идентификатор Git-коммита.

Подставьте имя этой серии.

    MAIN_BATCH="results/raw/ИМЯ_ОСНОВНОЙ_СЕРИИ"
    make validate BATCH="$MAIN_BATCH"

Для основной серии сообщение «A/A не запрошена для этой серии» является ожидаемым. A/A выполнялась отдельно.

Здесь проверяются нагрузка и стабильность, а обычный анализ сравнивает подходы.

Если нужны только таблицы и графики без проверки стабильности, используется make analyze с тем же BATCH.

## 7. Где смотреть результаты

Результаты обработки находятся в results/processed/ИМЯ_ОСНОВНОЙ_СЕРИИ. Открывайте файлы из этой папки в редакторе, просмотрщике изображений или программе для таблиц.

| Файл | Что содержит |
| --- | --- |
| *runs.csv* | Показатели каждого отдельного прогона |
| *summary.csv* | Число измерений, медиану, разброс и доверительные интервалы |
| *comparisons.csv* | Сравнения подходов, размер эффекта и p_holm с поправкой на множественные сравнения |

Для оценки времени выполнения сначала рассмотрите три графика.

1. *sequential-scenarioDurationMs.png* для последовательной обработки.
2. *concurrent-scenarioDurationMs.png* для одновременных первых обращений.
3. *repeated-scenarioDurationMs.png* для повторных вызовов.

На них представлены отдельные наблюдения, изменение времени по порядку запуска и доля прогонов, завершившихся за заданное время.

Графики с окончанием *wasmInstanceCount.png* показывают число экземпляров, а *wasmLinearMemoryBytes.png* объём линейной памяти WASM. Это не вся память браузера.

В подпапке validation находятся *resources.png*, *resources.csv*, *trends.csv* и текстовый протокол *validation.txt*.

Успешное выполнение команды означает, что обработка завершилась. Вывод о качестве измерений делается по протоколу и графикам.

При повторении эксперимента времена могут отличаться от сохранённых. На них влияют характеристики компьютера и условия запуска.

## 8. Повторение основной серии

Сохраните первую серию и её обработку перед следующим запуском.

    git add results test-results
    git diff --cached --stat
    git commit -m "Результаты основной серии эксперимента"
    git status --short

При чистой рабочей копии повторите эксперимент с той же конфигурацией и квотой.

    EXPERIMENT_CPUS=6 make experiment

Для новой папки выполните обработку.

    REPEAT_BATCH="results/raw/ИМЯ_ПОВТОРНОЙ_СЕРИИ"
    make validate BATCH="$REPEAT_BATCH"

Сопоставьте summary.csv, comparisons.csv и графики двух серий. Проверьте, сохраняются ли различия по времени, числу экземпляров и памяти.

Серии автоматически не объединяются.

Коммит результатов изменит хеш Git, но при отсутствии правок исходников и конфигурации исследуемый код останется тем же.

## 9. Остановка стенда

    make down

Команда останавливает контейнеры проекта. Измерения и графики остаются на компьютере в results.

## Анализ уже сохранённых измерений

Можно проверить анализ без новых браузерных прогонов. Для этого достаточно Docker, Compose, make и копии репозитория.

    make validate BATCH=results/raw/wasm-integration-2026-11-12T17-15-27.114Z-e6fb67b9
    make validate BATCH=results/raw/wasm-integration-2026-11-13T07-39-27.843Z-c7a478f1

Повторная обработка обновляет файлы соответствующих папок results/processed.

Список всех серий и пояснение к версиям кода находятся в *results/README.md*.

В двух сохранённых основных сериях shared использовал один экземпляр и меньше линейной памяти. Различия по времени подтвердились для sequential и repeated.

Для concurrent значимого различия полного времени после поправки на множественные сравнения не обнаружено. Эти выводы относятся к выбранной нагрузке и окружению.

## Устройство репозитория

| Каталог | Назначение |
| --- | --- |
| *sut* | Приложение, вычислительный компонент и обёртка для работы с WASM |
| *docker* | Настройки сборки контейнеров и серверов |
| *configs* | Параметры экспериментальных серий |
| *runner* | Запуск браузера и сохранение измерений |
| *analysis* | Обработка данных и проверка стенда |
| *results/raw* | Исходные измерения и метаданные |
| *results/processed* | Таблицы, графики и протоколы проверки |

Для основных частей проекта подготовлены отдельные README с описанием реализации.

Для быстрой проверки запуска без основной серии предусмотрена команда make quick. Она выполняет девять прогонов и не предназначена для статистического сравнения. Для обычного воспроизведения достаточно шагов выше.
